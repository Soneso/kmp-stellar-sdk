# Migrating to 1.16.0

This guide covers the observable changes between 1.15.0 and 1.16.0. If you upgrade from an older version, also review the CHANGELOG between your version and 1.15.0 and the earlier migration guides, newest first: [1.15.0](1.15.0.md), [1.12.0](1.12.0.md). Each note describes one situation: whether you are affected, how it shows, and what to do.

## Contract addresses

- If you pass an address other than a contract (`C...`) address as the contract to `InvokeHostFunctionOperation.invokeContractFunction` or `ContractClient.forContractWithoutSpec`, a muxed contract (`W...`) included: in 1.16.0 the call throws `IllegalArgumentException`. For a muxed contract the message is `The contract to invoke must be a contract (C...) address, got a muxed contract (W...) address: <address>; use its base contract (C...) address`, and for another kind it names that kind, for example `got an account (G...) address: <address>`. In 1.15.0 `invokeContractFunction` encoded every address kind that `Address` parses into the invocation, and `forContractWithoutSpec` stored the identifier without a check. Pass the contract address, for a muxed contract `MuxedContract(address).contractId`.

  ```kotlin
  // 1.15.0
  val operation = InvokeHostFunctionOperation.invokeContractFunction(muxedContract, "increment", emptyList())
  ```

  ```kotlin
  // 1.16.0
  val operation = InvokeHostFunctionOperation.invokeContractFunction(MuxedContract(muxedContract).contractId, "increment", emptyList())
  ```

- If you pass an address other than a contract (`C...`) address to `ContractClient.forContract`, `SorobanServer.loadContractCodeForContractId`, or `SorobanServer.loadContractInfoForContractId`: in 1.16.0 the call throws `IllegalArgumentException` before any request. The message starts `The contract to load must be a contract (C...) address` and names the kind given, as for the invocation. In 1.15.0 the SDK requested the contract instance entry stored under that address. Pass the contract address, for a muxed contract `MuxedContract(address).contractId`, and catch `IllegalArgumentException` where the address comes from user input.

- If you call `SorobanServer.getContractData` with an owner that is not a contract (`C...`) address, or with a key that holds a muxed address: in 1.16.0 the call throws `IllegalArgumentException` before any request. The owner message starts `The contract data owner must be a contract (C...) address` and names the kind given. A key that is or holds a muxed account (`M...`) or muxed contract (`W...`) address at any depth of its vectors and maps gives `Contract data keys cannot contain muxed account (M...) or muxed contract (W...) addresses`. In 1.15.0 the SDK sent the ledger entry request with the owner and key given. Pass the contract as owner, and build keys from base addresses, `MuxedAccount(address).accountId` or `MuxedContract(address).contractId`.

- If you match the message of the `IllegalArgumentException` that `SorobanServer.getSACBalance` throws for a holder that is not a contract (`C...`) address: in 1.16.0 the message names the kind given, for example `The balance holder must be a contract (C...) address, got an account (G...) address: <address>`. For a secret seed it reads `The balance holder must be a contract (C...) address, got a secret seed (S...) instead of an address`, without the seed. In 1.15.0 the message was `Invalid contract ID: <address>` for every input. Match on the exception type, or update the pattern.

## stellar.toml parsing

- If you read values from `StellarToml.parse` or `StellarToml.fromDomain` for a file with escapes in basic strings, literal (`'...'`) or multi-line strings, inline comments, or arrays that nest across lines: in 1.16.0 these values are the ones TOML 1.0 defines, so `ORG_NAME = "Example Org" # legal name` gives `Example Org`. In 1.15.0 basic strings kept their escapes as written, literal strings kept their quotes, and a value with an inline comment kept its quotes and the comment, `"Example Org" # legal name`. Multi-line strings kept extra quotes or lost their content, and a multi-line array ended at the first line ending in `]`. Remove post-processing that strips quotes or comments or decodes escapes.

## Integer arguments of ContractSpec

- If you pass a value beyond the `Long` range for a u64, timepoint, duration, 128-bit, or 256-bit parameter through `ContractSpec` or a `ContractClient` argument map: in 1.16.0 a `BigInteger`, a `ULong`, or a decimal `String` converts with its full value. A value outside the type's range throws `ContractSpecException` with `Invalid type: Value <value> out of range for <type>`; `ContractClient.invoke` wraps it in `IllegalArgumentException`. In 1.15.0 every integer passed through `Long`: a `BigInteger` threw `ContractSpecException` with `Invalid type: Expected integer type, got BigInteger for <type>`, a longer decimal string failed to parse, and a `ULong` above `Long.MAX_VALUE` wrapped to a negative value. Pass the value directly. A prebuilt `SCValXdr`, such as `Scv.toInt128(value)`, keeps working.

- If you pass a `ULong` above `Long.MAX_VALUE` for a u32, i32, or i64 parameter through `ContractSpec` or a `ContractClient` argument map: in 1.16.0 the conversion throws `ContractSpecException`, with `Invalid type: Value 18446744073709551615 out of range for u32` for `ULong.MAX_VALUE` and a u32 parameter. `ContractClient.invoke` wraps it in `IllegalArgumentException`. In 1.15.0 the value wrapped to a negative `Long`. An i64 parameter encoded it, `ULong.MAX_VALUE` as `-1`. An i32 parameter encoded the wrapped value when it lay within its range and rejected it otherwise. A u32 parameter rejected it with `Invalid type: Value -1 out of range for u32`. Pass a value within the parameter's range. An i64 parameter takes a `ULong` up to `Long.MAX_VALUE`.

- If you pass a `Double` or `Float` for an integer parameter through `ContractSpec` or a `ContractClient` argument map: in 1.16.0 a whole value converts exactly within the type's range, so `1e19` encodes as `10000000000000000000` for an i128. A fractional, NaN, or infinite value throws `ContractSpecException`, with `Invalid type: Value 3.75 is not an integer for i128` for `3.75`. `ContractClient.invoke` wraps it in `IllegalArgumentException`. In 1.15.0 the SDK cut the fraction, turned NaN into 0, and clamped values beyond the `Long` range to `Long.MIN_VALUE` or `Long.MAX_VALUE`. Round values with a fraction before you pass them.

## Signing and submitting with AssembledTransaction

- If you call `AssembledTransaction.signAuthEntries` on a transaction with a memo, or read the fee of the transaction it rebuilds: in 1.16.0 the rebuilt transaction keeps the memo and the fee of the simulated transaction. In 1.15.0 the rebuild dropped the memo and set a fee that counted the resource fee twice. Calls need no change. Remove a step that rebuilt the transaction to restore the memo or the fee.

- If you call `AssembledTransaction.submit` or `signAndSubmit`, directly or through `ContractClient.invoke`, and handle a failure of the status requests after the send: in 1.16.0 a failed `getTransaction` request does not end the polling. When `ClientOptions.submitTimeout` runs out, `submit` throws `TransactionStillPendingException` if a status request returned a response, and the last request failure if every one failed. In 1.15.0 the first failed status request ended `submit` with that failure. Remove a retry that called `submit` again after a failed status request, and keep handling `TransactionStillPendingException`.

## stellar.toml fetching

- If you pass `StellarToml.fromDomain` a domain with a scheme, path, user info, or whitespace, such as `https://example.com`: in 1.16.0 the call throws `IllegalArgumentException` with `Invalid stellar.toml domain 'https://example.com': expected a host with an optional port` before any request. In 1.15.0 the SDK placed the string into the URL `https://<domain>/.well-known/stellar.toml` and sent the request. Pass the host with an optional port, such as `example.com` or `localhost:8000`, and catch `IllegalArgumentException` where the domain comes from user input.

- If you call `StellarToml.fromDomain` or `StellarToml.currencyFromUrl` without an `httpClient` and the server is slow to connect or to answer: in 1.16.0 the client the SDK creates gives up on the connection after 10 seconds and on the request after 30 seconds, with the Ktor exception `ConnectTimeoutException` or `HttpRequestTimeoutException`. In 1.15.0 that client set no timeout, so the defaults of the Ktor engine applied. Pass your own `HttpClient` with longer timeouts where a server needs them; the SDK uses an injected client as given.

- If you fetch a stellar.toml or currency TOML file larger than 102,400 bytes with `StellarToml.fromDomain` or `StellarToml.currencyFromUrl`: in 1.16.0 the call throws `IllegalStateException` with `TOML file exceeds 102400 bytes`. In 1.15.0 the SDK read and parsed a file of any size. SEP-1 limits the file to 100 KB, so ask its publisher to shrink it. To read a larger stellar.toml anyway, fetch it yourself and pass the text to `StellarToml.parse`, which sets no size limit.
