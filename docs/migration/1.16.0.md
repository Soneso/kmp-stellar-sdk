# Migrating to 1.16.0

This guide covers the observable changes between 1.15.0 and 1.16.0. If you upgrade from an older version, also review the CHANGELOG between your version and 1.15.0 and the earlier migration guides, newest first: [1.15.0](1.15.0.md), [1.12.0](1.12.0.md). Each note describes one situation: whether you are affected, how it shows, and what to do.

## stellar.toml parsing

- If you read values from `StellarToml.parse` or `StellarToml.fromDomain` for a file with escapes in basic strings, literal (`'...'`) or multi-line strings, inline comments, or arrays that nest across lines: in 1.16.0 these values are the ones TOML 1.0 defines, so `ORG_NAME = "Example Org" # legal name` gives `Example Org`. In 1.15.0 basic strings kept their escapes as written, literal strings kept their quotes, and a value with an inline comment kept its quotes and the comment, `"Example Org" # legal name`. Multi-line strings kept extra quotes or lost their content, and a multi-line array ended at the first line ending in `]`. Remove post-processing that strips quotes or comments or decodes escapes.

## Integer arguments of ContractSpec

- If you pass a `Double` or `Float` for an integer parameter through `ContractSpec` or a `ContractClient` argument map: in 1.16.0 a whole value converts exactly within the type's range, so `1e19` encodes as `10000000000000000000` for an i128. A fractional, NaN, or infinite value throws `ContractSpecException`, with `Invalid type: Value 3.75 is not an integer for i128` for `3.75`. `ContractClient.invoke` wraps it in `IllegalArgumentException`. In 1.15.0 the SDK cut the fraction, turned NaN into 0, and clamped values beyond the `Long` range to `Long.MIN_VALUE` or `Long.MAX_VALUE`. Round values with a fraction before you pass them.

## Signing and submitting with AssembledTransaction

- If you call `AssembledTransaction.signAuthEntries` on a transaction with a memo, or read the fee of the transaction it rebuilds: in 1.16.0 the rebuilt transaction keeps the memo and the fee of the simulated transaction. In 1.15.0 the rebuild dropped the memo and set a fee that counted the resource fee twice. Calls need no change. Remove a step that rebuilt the transaction to restore the memo or the fee.

- If you call `AssembledTransaction.submit` or `signAndSubmit`, directly or through `ContractClient.invoke`, and handle a failure of the status requests after the send: in 1.16.0 a failed `getTransaction` request does not end the polling. When `ClientOptions.submitTimeout` runs out, `submit` throws `TransactionStillPendingException` if a status request returned a response, and the last request failure if every one failed. In 1.15.0 the first failed status request ended `submit` with that failure. Remove a retry that called `submit` again after a failed status request, and keep handling `TransactionStillPendingException`.

## stellar.toml fetching

- If you call `StellarToml.fromDomain` or `StellarToml.currencyFromUrl` without an `httpClient` and the server is slow to connect or to answer: in 1.16.0 the client the SDK creates gives up on the connection after 10 seconds and on the request after 30 seconds, with the Ktor exception `ConnectTimeoutException` or `HttpRequestTimeoutException`. In 1.15.0 that client set no timeout, so the defaults of the Ktor engine applied. Pass your own `HttpClient` with longer timeouts where a server needs them; the SDK uses an injected client as given.

- If you fetch a stellar.toml or currency TOML file larger than 102,400 bytes with `StellarToml.fromDomain` or `StellarToml.currencyFromUrl`: in 1.16.0 the call throws `IllegalStateException` with `TOML file exceeds 102400 bytes`. In 1.15.0 the SDK read and parsed a file of any size. SEP-1 limits the file to 100 KB, so ask its publisher to shrink it. To read a larger stellar.toml anyway, fetch it yourself and pass the text to `StellarToml.parse`, which sets no size limit.
