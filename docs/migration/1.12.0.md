# Migrating to 1.12.0

This guide covers the observable changes between 1.11.0 and 1.12.0. If you upgrade from an older version, also review the release notes between your version and 1.11.0. Each note describes one situation: whether you are affected, how it shows, and what to do.

- If you simulate Soroban transactions or read auth entries from simulation: in 1.12.0, `SorobanServer.simulateTransaction` / `prepareTransaction`, `SimulateTransactionRequest`, and `ClientOptions` default `useUpgradedAuth` to true and always send the key. Simulation against a Protocol 27+ RPC returns entries carrying `ADDRESS_V2` credentials, and a `when` or `is SorobanCredentialsXdr.Address` match over them does not match: their arm is `SorobanCredentialsXdr.AddressV2`. In 1.11.0 the key was omitted unless set, and simulation returned `SorobanCredentialsXdr.Address` entries. On a network below Protocol 27, pass `useUpgradedAuth = false`: `ADDRESS_V2` entries invalidate the transaction there.
- If you passed `null` for `useUpgradedAuth`: in 1.12.0 the parameters are `Boolean`, so `null` is a compile error. In 1.11.0 they were `Boolean?`. Pass `true` or omit the argument. Precompiled JVM and Android consumers hit `NoSuchMethodError` on these signatures (`simulateTransaction`, `prepareTransaction`, the `SimulateTransactionRequest` constructor and `copy()`) until rebuilt against 1.12.0.
- If you call `Auth.authorizeInvocation`: in 1.12.0 it builds `ADDRESS_V2` credentials by default. In 1.11.0 it built legacy `ADDRESS` credentials unless `authV2 = true` was passed. Pass `authV2 = false` to keep building legacy entries, for example on a pre-Protocol-27 network.
- OpenZeppelin smart accounts: if your relayer rejects submissions after the upgrade (it cannot parse Protocol 27 authorization XDR), set `useUpgradedAuth = false` in `OZSmartAccountConfig`. If an external wallet fails to sign (it cannot sign the address-bound preimage type), set `useUpgradedAuthForWalletSigners = false`. Each flag controls only its own path. Direct callers of `SmartAccountAuth.buildSourceAccountAuthPayloadHash` get a compile error: pass the address the credentials will carry as the second argument, and `useUpgradedAuth = false` when building legacy credentials, so the hash matches the credential arm. In 1.11.0 the constructor and `copy()` of `OZSmartAccountConfig` had other JVM signatures, so precompiled consumers must rebuild.
- If you read the CAP-85 executable tag: in 1.12.0, `ContractExecutableExternalRefXdr.tag` and the `SCValXdr.ExecutableTag` payload are `ByteArray`, and code reading them as strings gets a compile error. In 1.11.0 both were `SCStringXdr`. Read text tags through `tagString`, which throws `CharacterCodingException` on a tag that is not valid UTF-8, or `Scv.fromExecutableTag`, which throws `IllegalArgumentException`; catch the type your reader throws. For tags that are not text, `Scv.toExecutableTagBytes` / `fromExecutableTagBytes`, `ContractExecutableExternalRefXdr.tag`, and `SCValXdr.ExecutableTag.value` carry the exact bytes. Building from text keeps compiling: the `ContractExecutableExternalRefXdr(owner, tag: String)` factory and `Scv.toExecutableTag(String)` encode UTF-8 once.
- If you compare values carrying a tag, or use them as `Map` keys or in a `Set`: both tag positions live in data classes over `ByteArray`, so `==` and `hashCode` follow array identity. Two equal-bytes tags read from two decodes compare unequal, and a map lookup by a re-decoded key misses. Compare tags via `contentEquals`, key maps by the string views or the hex of the bytes.
- If you build keys, addresses, or signers from user input or storage: in 1.12.0, strkey decoding is strict on every platform. Trailing `=` padding, whitespace anywhere in the string, lowercase base32, non-ASCII characters, and wrong lengths all raise `IllegalArgumentException`, and malformed input never raises `IndexOutOfBoundsException`. In 1.11.0 several of these inputs decoded on JVM and Android, and some malformed input raised `IndexOutOfBoundsException`. Trim and normalize pasted input before validating it.
- If you store `P...` signed-payload strkeys, build them with `StrKey.encodeSignedPayload`, or gate on `StrKey.isValidSignedPayload`: in 1.12.0, decode and encode enforce the SEP-23 framing rules (payload length 1..64, exact data size, zero padding after the payload). A malformed stored value raises `IllegalArgumentException` naming the broken rule, and `isValidSignedPayload` returns false for it. In 1.11.0 such a value validated and decoded, and two of the three SEP-23 malformed test vectors round-tripped to a different strkey with surplus bytes dropped. Re-derive stored signed-payload strkeys from the signer key and payload rather than trusting the stored string; it may name a different signer than intended.
- If you validate or construct claimable-balance addresses from stored or third-party `B...` strkeys: in 1.12.0, a strkey carrying a non-V0 discriminant fails at `StrKey.decodeClaimableBalance`, the `Address` constructor, and XDR-JSON decoding with `IllegalArgumentException`, and `StrKey.isValidClaimableBalance` returns false for it. In 1.11.0 such a value decoded, reported `AddressType.CLAIMABLE_BALANCE`, and re-encoded, and only `toSCAddress()` refused it.
- If you parse hex ids or hashes: in 1.12.0, hex carrying a sign character or non-ASCII digits is rejected with `IllegalArgumentException` across memos, liquidity-pool operations, contract creation, contract-spec arguments, and OZ credential storage, and contract-spec hex rejects interior spaces. In 1.11.0 such input produced different bytes than its characters spell (`"-1"` read as the byte `0xFF`) or failed with `NumberFormatException`, and contract-spec hex tolerated interior spaces.
- If you call `loadContractCodeForWasmId` or `loadContractInfoForWasmId`: in 1.12.0, a wasm id that is not exactly 64 hex characters is rejected at the call with a message naming the rule. In 1.11.0 it failed deeper, with a generic XDR-writer message.
- If you store or compare claimable balance ids: in 1.12.0, `Sponsorship.ClaimableBalance` read from parsed XDR reports the 72-character hex form Horizon serves, so comparisons against stored ids can fail on the spelling. In 1.11.0 it reported the bare 64-character hash. Normalize either side with `ClaimableBalanceId.forId(stored).toPaddedHex()`, which accepts every spelling. Everything you pass into the SDK keeps working: the operations and request builders accept the strkey and all three hex widths and validate at construction. A malformed balance id raises `IllegalArgumentException` at the builder or constructor call, before any request, so wrap that call as well as the request.
- If you call `EffectsRequestBuilder.forClaimableBalance`: it is removed (compile error). Horizon serves no effects-by-claimable-balance route, so the method could only build requests that fail. Query the balance's operations or transactions instead.
- If you pin or compare the XDR your deployments submit: in 1.12.0, `ContractClient.deploy` and `deployFromWasmId` always submit the `CREATE_CONTRACT_V2` host function, with an empty constructor vector when no arguments are given. In 1.11.0 they submitted plain `CREATE_CONTRACT` in that case. The on-chain result is the same. The plain form stays available through `InvokeHostFunctionOperation.createContract`.
- If you load contracts that may carry a CAP-85 external-reference executable: in 1.12.0 they resolve and load, and an unresolvable reference throws `IllegalStateException` naming the owner and the tag. In 1.11.0 `forContract` failed with "Contract spec not found" for them, and the loaders answered null. A null from the loaders means instance or code not found, or a Stellar Asset Contract.
- If you send amount strings with trailing zeros: in 1.12.0, `"0.50000000"` builds 0.5, because the seven-decimal limit counts significant decimals, and an amount with a sign character inside the fraction is rejected. In 1.11.0 every operation rejected `"0.50000000"`, and `"1.-5"` built 0.95 silently.
- If you read asset balance changes from invoke-host-function operations: in 1.12.0, `AssetContractBalanceChange.from` and `.to` are nullable, because Horizon omits `from` on a mint and `to` on a burn or clawback. In 1.11.0 an operations page carrying such a change failed to parse as a whole. Unwrap where you read them.
- If you call `Sep08Service.fromDomain` on JVM or Android: in 1.12.0, construction fails when the anchor's `stellar.toml` names a `CURRENCIES` issuer that is not a canonical strkey, for example with whitespace inside the quotes, which the TOML parser preserves. In 1.11.0 it failed that way on JavaScript and Native only. The toml is the anchor's to fix: catch the `IllegalArgumentException` and report the anchor's configuration.
- If you configured a SEP-12 callback signing key with stray whitespace or lowercase: in 1.12.0, signature verification fails closed. The verifier throws no exception, returns false, and callbacks are rejected. In 1.11.0 such a key decoded on JVM and Android, and verification could pass. Normalize the configured key to the canonical strkey.
- If you cancel coroutines during SEP-10 or SEP-45 challenge validation: in 1.12.0, cancellation propagates as `CancellationException`. In 1.11.0 it was reported as an invalid server signature.
