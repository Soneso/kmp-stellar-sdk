# Migrating to 1.12.0

This guide covers the observable changes between 1.11.0 and 1.12.0. If you upgrade from an older version, also review the release notes between your version and 1.11.0. Each note describes one situation: whether you are affected, how it shows, and what to do.

- If you simulate Soroban transactions or read auth entries from simulation: `SorobanServer.simulateTransaction` / `prepareTransaction`, `SimulateTransactionRequest`, and `ClientOptions` now default `useUpgradedAuth` to true and always send the key, so simulation against a Protocol 27+ RPC returns entries carrying `ADDRESS_V2` credentials. A `when` or `is SorobanCredentialsXdr.Address` match over simulation entries no longer matches them — the arm is `SorobanCredentialsXdr.AddressV2`. On a network below Protocol 27, pass `useUpgradedAuth = false`: `ADDRESS_V2` entries invalidate the transaction there.
- If you passed `null` for `useUpgradedAuth`: the parameters are `Boolean` now (were `Boolean?`), so `null` is a compile error — pass `true` or omit the argument. Precompiled JVM and Android consumers hit `NoSuchMethodError` on the changed signatures (`simulateTransaction`, `prepareTransaction`, the `SimulateTransactionRequest` constructor and `copy()`) until rebuilt against 1.12.0.
- If you call `Auth.authorizeInvocation`: it builds `ADDRESS_V2` credentials by default now. Pass `authV2 = false` to keep building legacy entries, for example on a pre-Protocol-27 network.
- OpenZeppelin smart accounts: if your relayer rejects submissions after the upgrade (it cannot parse Protocol 27 authorization XDR), set `useUpgradedAuth = false` in `OZSmartAccountConfig`; if an external wallet can no longer sign (it cannot sign the address-bound preimage type), set `useUpgradedAuthForWalletSigners = false`. Each flag controls only its own path. Direct callers of `SmartAccountAuth.buildSourceAccountAuthPayloadHash` get a compile error: pass the address the credentials will carry as the new second argument, and `useUpgradedAuth = false` when building legacy credentials, so the hash matches the credential arm. Precompiled consumers of `OZSmartAccountConfig` must rebuild — its constructor and `copy()` signatures changed.
- If you read the CAP-85 executable tag: `ContractExecutableExternalRefXdr.tag` and the `SCValXdr.ExecutableTag` payload are `ByteArray` now (both shipped in 1.11.0 as `SCStringXdr`). Code reading them as strings gets a compile error. Read text tags through `tagString` (throws `CharacterCodingException` on non-UTF-8) or `Scv.fromExecutableTag` (throws `IllegalArgumentException`), so a binary tag surfaces as an exception rather than replacement characters — catch the type your reader actually throws. For tags that are not text, `Scv.toExecutableTagBytes` / `fromExecutableTagBytes`, `ContractExecutableExternalRefXdr.tag`, and `SCValXdr.ExecutableTag.value` carry the exact bytes. Building from text keeps compiling: the `ContractExecutableExternalRefXdr(owner, tag: String)` factory and `Scv.toExecutableTag(String)` encode UTF-8 once.
- If you compare values carrying a tag, or use them as `Map` keys or in a `Set`: both tag positions live in data classes over `ByteArray`, so `==` and `hashCode` follow array identity — two equal-bytes tags read from two decodes compare unequal, and a map lookup by a re-decoded key misses. Compare tags via `contentEquals`, key maps by the string views or the hex of the bytes.
- If you build keys, addresses, or signers from user input or storage: strkey decoding is strict on every platform now. Trailing `=` padding, whitespace anywhere in the string, lowercase base32, non-ASCII characters, and wrong lengths all raise `IllegalArgumentException` — on JVM and Android, several of these previously decoded. Trim and normalize pasted input before validating it. The exception type also unifies: malformed input raises `IllegalArgumentException` everywhere, never `IndexOutOfBoundsException`.
- If you store `P...` signed-payload strkeys, build them with `StrKey.encodeSignedPayload`, or gate on `StrKey.isValidSignedPayload`: the SEP-23 framing rules (payload length 1..64, exact data size, zero padding after the payload) are enforced on decode and encode now. A malformed stored value that previously validated and decoded raises `IllegalArgumentException` naming the broken rule, and `isValidSignedPayload` returns false where it returned true. Two of the three SEP-23 malformed test vectors previously round-tripped to a different strkey with surplus bytes silently dropped — so re-derive stored signed-payload strkeys from the signer key and payload rather than trusting the stored string; it may name a different signer than intended.
- If you validate or construct claimable-balance addresses from stored or third-party `B...` strkeys: a strkey carrying a non-V0 discriminant fails at `StrKey.decodeClaimableBalance`, the `Address` constructor, and XDR-JSON decoding now (`IllegalArgumentException`), and `StrKey.isValidClaimableBalance` returns false for it. Such a value previously decoded, reported `AddressType.CLAIMABLE_BALANCE`, and re-encoded; only `toSCAddress()` refused it — the failure moves from that one call to the entry points.
- If you parse hex ids or hashes: hex carrying a sign character or non-ASCII digits is rejected with `IllegalArgumentException` across memos, liquidity-pool operations, contract creation, contract-spec arguments, and OZ credential storage. Such input previously produced different bytes than its characters spell (`"-1"` read as the byte `0xFF`) or failed with `NumberFormatException`. Contract-spec hex no longer tolerates interior spaces.
- If you call `loadContractCodeForWasmId` or `loadContractInfoForWasmId`: a wasm id that is not exactly 64 hex characters is rejected at the call with a message naming the rule; it previously failed deeper, with a generic XDR-writer message.
- If you store or compare claimable balance ids: `Sponsorship.ClaimableBalance` read from parsed XDR reports the 72-character hex form Horizon serves (previously the bare 64-character hash), so comparisons against stored ids can fail on the spelling. Normalize either side with `ClaimableBalanceId.forId(stored).toPaddedHex()` — it accepts every spelling. Everything you pass into the SDK keeps working: the operations and request builders accept the strkey and all three hex widths, and validate at construction — an id naming no balance raises `IllegalArgumentException` at the builder or constructor call, before any request, so error handling wrapped around the request alone no longer catches it.
- If you call `EffectsRequestBuilder.forClaimableBalance`: it is removed (compile error). Horizon serves no effects-by-claimable-balance route, so the method could only build requests that fail. Query the balance's operations or transactions instead.
- If you pin or compare the XDR your deployments submit: `ContractClient.deploy` and `deployFromWasmId` always submit the `CREATE_CONTRACT_V2` host function now, with an empty constructor vector when no arguments are given; they previously submitted plain `CREATE_CONTRACT` in that case. The on-chain result is unchanged. The plain form stays available through `InvokeHostFunctionOperation.createContract`.
- If you load contracts that may carry a CAP-85 external-reference executable: they resolve and load now — `forContract` previously failed with "Contract spec not found" for them. The failure mode changed shape: an unresolvable reference throws `IllegalStateException` naming the owner and the tag, where the loaders previously answered null. A null from the loaders still means instance or code not found, or a Stellar Asset Contract.
- If you send amount strings with trailing zeros: `"0.50000000"` builds 0.5 now, where every operation previously rejected it — the seven-decimal limit counts significant decimals. Amounts with a sign character inside the fraction are rejected: `"1.-5"` previously built 0.95 silently.
- If you read asset balance changes from invoke-host-function operations: `AssetContractBalanceChange.from` and `.to` are nullable now — Horizon omits `from` on a mint and `to` on a burn or clawback, and an operations page carrying one previously failed to parse as a whole. Unwrap where you read them.
- If you call `Sep08Service.fromDomain` on JVM or Android: construction fails now when the anchor's `stellar.toml` names a `CURRENCIES` issuer that is not a canonical strkey (for example with whitespace inside the quotes, which the TOML parser preserves) — it already failed that way on JavaScript and Native. The toml is the anchor's to fix: catch the `IllegalArgumentException` and report the anchor's configuration rather than treating it as an SDK regression.
- If you configured a SEP-12 callback signing key with stray whitespace or lowercase: signature verification fails closed now — no exception, the verifier returns false and callbacks are rejected. On JVM and Android such a key previously decoded and verification could pass. Normalize the configured key to the canonical strkey.
- If you cancel coroutines during SEP-10 or SEP-45 challenge validation: cancellation propagates as `CancellationException` now; it was previously reported as an invalid server signature.
