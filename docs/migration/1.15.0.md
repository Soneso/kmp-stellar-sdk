# Migrating to 1.15.0

This guide covers the observable changes between 1.14.0 and 1.15.0. If you upgrade from an older version, also review the CHANGELOG between your version and 1.14.0 and the earlier migration guides, newest first: [1.12.0](1.12.0.md). Each note describes one situation: whether you are affected, how it shows, and what to do.

## Asset codes in XDR-JSON

- If you decode XDR-JSON written by hand or by another tool that holds a twelve-character asset code (`AssetCode12Xdr`, the `credit_alphanum12` asset) shorter than five bytes: in 1.15.0 decoding throws `IllegalArgumentException` with the message `AssetCode12Xdr: expects an asset code of at least 5 bytes, got 3` for the document `"ABC"`. In 1.14.0 such a string decoded to an asset code that the network rejects as invalid. Write the short code with escaped NUL bytes up to five bytes, the document `"ABC\\0\\0"` for a three-character code. XDR-JSON that the SDK writes already has this form, and `AssetCode4Xdr` is unaffected.

## Contract address parameters

- If you pass a muxed address (`M...` or `W...`) for an `Address` parameter, through `ContractSpec` or a `ContractClient` argument map: in 1.15.0 the conversion throws `ContractSpecException`, for a muxed account with `Invalid type: Address takes an account (G...) or contract (C...) address, got the muxed address <address>, which needs a MuxedAddress parameter`. In 1.14.0 the SDK converted every address kind it could parse. Pass the account behind a muxed account, `MuxedAccount(address).accountId`, or the contract behind a muxed contract, `MuxedContract(address).contractId`. `MuxedAddress` parameters keep taking `M...` and `W...`.

  ```kotlin
  // 1.14.0
  val args = spec.funcArgsToXdrSCValues("balance", mapOf("id" to muxedAddress))
  ```

  ```kotlin
  // 1.15.0
  val args = spec.funcArgsToXdrSCValues("balance", mapOf("id" to MuxedAccount(muxedAddress).accountId))
  ```

- If you pass a claimable balance (`B...`) or liquidity pool (`L...`) address for an `Address` or `MuxedAddress` parameter through `ContractSpec` or a `ContractClient` argument map: in 1.15.0 the conversion throws `ContractSpecException` with `Invalid type: <expected>, got the claimable balance address <address>, which is produced by the host and is not a contract input`, and with `liquidity pool address` in place of `claimable balance address` for `L...`. `<expected>` names the kinds the parameter takes, for example `Address takes an account (G...) or contract (C...) address`. In 1.14.0 the SDK converted the address to the claimable balance or liquidity pool arm of `SCAddress`. Pass the account or contract address the parameter asks for.

- If you convert an `Address` to a string before passing it as a contract argument: in 1.15.0 an `Address` instance converts directly, of type `ACCOUNT` or `CONTRACT` for an `Address` parameter, and also `MUXED_ACCOUNT` or `MUXED_CONTRACT` for a `MuxedAddress` parameter. In 1.14.0 every `Address` instance threw `ContractSpecException` with `Invalid type: Expected String address, got Address`. Keep the string conversion or pass the instance; both produce the same argument.

- If you match the messages of `ContractSpecException` for address parameters: in 1.15.0 a malformed string gives `Invalid type: Invalid address format: <value>; <expected>`, and a value of another type gives `Invalid type: <expected>, got <type>`. `<expected>` is `Address takes an account (G...) or contract (C...) address` or `MuxedAddress takes an account (G...), muxed account (M...), contract (C...) or muxed contract (W...) address`, and `<type>` is the class name of the value. In 1.14.0 the messages were `Invalid type: Invalid address format: <value> - <cause>` and `Invalid type: Expected String address, got <type>`. Match on the exception type, or update the patterns.

## XDR definitions 579a90b

- If you match with `when` over `SCAddressXdr`, `SCAddressTypeXdr`, `ContractCostTypeXdr`, or `Address.AddressType` without an `else` branch: in 1.15.0 the match does not compile, because the types gain `SCAddressXdr.MuxedContract`, `SC_ADDRESS_TYPE_MUXED_CONTRACT`, the nine members `MlDsa44DecodeVerifyingKey` through `VerifyMlDsa87Sig`, and `MUXED_CONTRACT`. In 1.14.0 decoding address type 5 or a cost type from 86 to 94 threw `IllegalArgumentException` with `Unknown SCAddressTypeXdr value: 5` or `Unknown ContractCostTypeXdr value: <value>`. Add the new branches or an `else` branch. Code that caught that exception receives the new arms instead.

## Soroban authorization with muxed addresses

- If you sign with `Auth.authorizeEntry` an entry whose credential address or `forAddress` target is a muxed address, pass one as the `publicKey` of `Auth.authorizeInvocation`, or as a delegate to `Auth.attachDelegates`: in 1.15.0 the call throws `IllegalArgumentException` with `Muxed account (M...) and muxed contract (W...) addresses are not valid Soroban auth addresses: <address>`, and with `delegate addresses` in place of `auth addresses` for a delegate. In 1.14.0 a muxed credential address was signed without a check, and an `M...` target or delegate failed with `Muxed (M...) addresses are not valid Soroban auth addresses: <address>` or its `delegate addresses` form. Sign for the account behind the muxed address, `MuxedAccount(address).accountId`, and update message patterns.

## XDR definitions c2612cf

- If you match with `when` over `StellarValueTypeXdr` or `StellarValueExtXdr` without an `else` branch: in 1.15.0 the match does not compile, because the types gain `STELLAR_VALUE_SIGNED_MS`, `STELLAR_VALUE_EMPTY_TX_SET_MS`, `StellarValueExtXdr.SignedMsValue`, and `StellarValueExtXdr.ProposedMsValue`. In 1.14.0 decoding a `StellarValueXdr` of either new type threw `IllegalArgumentException` with `Unknown StellarValueTypeXdr value: 3` or `Unknown StellarValueTypeXdr value: 4`. Add the new branches or an `else` branch. The new arms carry `closeTimeMs`, the ledger close time in milliseconds.

## Signature expiration of authorization entries

- If you pass `validUntilLedgerSequence` to `AssembledTransaction.signAuthEntries`, or `validUntilLedgerSeq` to `Auth.authorizeEntry`, for an entry another signer has signed: in 1.15.0 a value other than the entry's stored expiration throws `IllegalArgumentException` with `Signature expiration ledger <requested> differs from <stored>, the expiration ledger that signatures already on this authorization entry commit to`, and the transaction keeps its auth entries. In 1.14.0 each call stamped its own expiration, which invalidated the earlier signature. To reuse the stored expiration, omit the value on later `signAuthEntries` calls, or pass the stored value. A void or empty-vector signature counts as unsigned.

  ```kotlin
  // 1.14.0
  tx.signAuthEntries(owner, validUntilLedgerSequence = server.getLatestLedger().sequence + 100)
  tx.signAuthEntries(delegate, validUntilLedgerSequence = server.getLatestLedger().sequence + 100)
  ```

  ```kotlin
  // 1.15.0
  tx.signAuthEntries(owner, validUntilLedgerSequence = server.getLatestLedger().sequence + 100)
  tx.signAuthEntries(delegate)
  ```

## Map key order

- If you build map arguments with `Scv.toMap`, or pass a Kotlin `Map` or a struct to `ContractSpec` or `ContractClient.invoke`: in 1.15.0 the entries are sorted in the Soroban host's key order, which `compareScValHostOrder` implements, whatever the insertion order. In 1.14.0 the entries kept their insertion order, and the host rejected a call whose keys were out of its order. Calls need no change. A sort you added before encoding can go, and a test that compares the encoded XDR with an insertion-ordered map needs the sorted order. Decoding with `Scv.fromMap` keeps the wire order.

- If two map keys are equal in host order, for example two `Scv.toBytes` keys with the same contents from separate decodes, or two Kotlin keys that convert to the same value: in 1.15.0 `Scv.toMap` throws `IllegalArgumentException` with `Duplicate ScMap key: <key>`, and `ContractSpec` throws `ContractSpecException` with `Conversion failed: Duplicate ScMap key: <key>`, where `<key>` is the key's XDR-JSON. In 1.14.0 both entries were encoded, and the host rejected the map. Remove the duplicate. To build the entries yourself, use `Scv.toMap(List<SCMapEntryXdr>)`.

## Asset order and liquidity pools

- If you build a `LiquidityPool` from two credit assets with the same code and different issuers, or sort assets with `Asset.compareTo`: in 1.15.0 the issuers compare by their raw 32-byte public keys, as stellar-core does. A pair in the other order throws `IllegalArgumentException` with `Assets are not in lexicographic order. assetA must be < assetB. Current order: <assetA> vs <assetB>`. In 1.14.0 the SDK compared the issuers' strkey text, which reverses some pairs. Sort the pair before constructing the pool. Pools of different codes or asset types keep their order and pool id.

  ```kotlin
  // 1.14.0
  val pool = LiquidityPool(usdFromIssuerA, usdFromIssuerB)
  ```

  ```kotlin
  // 1.15.0
  val (assetA, assetB) = listOf(usdFromIssuerA, usdFromIssuerB).sorted()
  val pool = LiquidityPool(assetA, assetB)
  ```

## Diagnostic events of getTransaction

- If you read the diagnostic events of `SorobanServer.getTransaction` through `events?.diagnosticEventsXdr`, or decode them from the transaction meta yourself: in 1.15.0 `GetTransactionResponse.diagnosticEventsXdr` holds the list stellar-rpc sends, and `parseDiagnosticEventsXdr()` decodes it. In 1.14.0 the response had no top-level list, and `events?.diagnosticEventsXdr` stayed null because stellar-rpc does not send that field. Read the top-level list and drop the workaround. The nested `Events` members are deprecated and still decode the field in older response data.
